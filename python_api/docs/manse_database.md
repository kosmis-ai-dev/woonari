# SQL 원본 기반 만세력 DB

CR-009 · T-017 · T-018 / CR-010 · T-019. 사용자 제공 SQL Server export를 검증해 MySQL `woonari`에 적재합니다. 사주 계산은 이 DB의 음양력·간지·절입 값을 조회하고, 승인된 윤달 표시 교정표와 기존 ASP의 시간 보정 규칙을 적용합니다.

## 구축 및 재실행

프로젝트 루트에서 실행합니다. 원본 SQL을 DB 서버에서 직접 실행하지 않습니다. 지정된 `dbo.tb_manse` INSERT 형식만 파싱하며, 데이터는 파라미터로 적재합니다.

```sh
./woonari db import-manse /path/to/script.sql
./woonari db sync-manse
./woonari db check
./woonari stop
./woonari start
```

첫 명령은 `python_api/app/data/manse.sqlite3` 스냅샷을 원자적으로 생성합니다. 다음 명령은 MySQL `woonari.tb_manse`와 `woonari.woonari_manse_metadata`를 생성하고 전체 데이터를 한 트랜잭션으로 적재합니다. 같은 데이터면 다시 넣지 않으며, 기존 데이터가 다르면 보존하고 중단합니다. 다른 테이블은 변경하지 않습니다.

`.local/woonari/db/config.json`은 권한 600인 전용 설정 파일입니다. 계정·시크릿 ARN·암호를 소스에 넣지 않습니다.

```json
{
  "secret_arn": "<이 프로젝트 계정의 inter 시크릿 ARN>",
  "database": "woonari",
  "manse_backend": "mysql"
}
```

공식 실행기 `./woonari start`는 이 설정을 읽습니다. 시크릿 ARN의 리전으로 요청하고, Woonari 전용 AWS 프로필의 실제 계정을 검증합니다. TLS 인증서와 호스트명을 검증하며, 암호는 메모리에서만 사용합니다. 선택한 MySQL에 연결하지 못하면 계산 요청을 503으로 종료합니다. `/health`의 `calendar_backend`, 계산 결과의 `policy.data_backend`에서 선택된 저장소를 확인할 수 있습니다. 직접 실행하는 개발·테스트 기본값은 SQLite이며 원본 행은 동일합니다. 두 저장소 모두 같은 교정표를 적용합니다. `lunar_correction_version`은 현재 `lunar-leap-flags-v1`입니다.

## 원본 검증 결과

- UTF-16LE SQL Server export, `tb_manse` 18개 열·73,414행.
- 양력 1900-01-01~2100-12-31, 날짜 중복·누락 없음. 공개 API 범위는 기존 1900~2050년을 유지합니다.
- 원본 SHA256: `ab2ff0e3d305c0e58165f8b21c53a97d8a8ab31ac60c72ff0985fb28c1408205`.
- 정규화 데이터 SHA256: `ca09c072c91db082cdebb9050328352c8df665d91e1d89d9f2fa93da707f73ba`.
- 데이터 해시는 `idx` 순서의 18개 값 배열을 compact JSON UTF-8과 줄바꿈으로 직렬화한 전체 값입니다. `sDate`는 ISO 날짜로 보존합니다. 행 번호에서 날짜를 추측하지 않습니다.

원본에는 음력 `(2020,4,29,일반월)`, `(2023,2,29,일반월)`, `(2025,6,29,일반월)`, `(2028,5,29,일반월)`에 각각 양력 날짜가 2개 있습니다. 아래 교정표를 적용하는 API에서는 일반 달과 윤달이 정상 구분됩니다. 원본 데이터 자체의 진단 수와 해시는 그대로 보존합니다.

`1945-06-06`의 절기번호 8과 `2053-01-19 24:00` 기록도 보존합니다. 후자는 절기 창에서 다음 날 00:00으로 정규화합니다. 2024년 입춘은 원본에 있는 17:00을 적용하므로 이전 패키지의 17:27과 결과가 달라질 수 있습니다.

## 승인된 윤달 표시 교정

CR-010은 평달 마지막 날과 윤달 마지막 날의 `leafMon_YN` 오류 10행만 교정합니다. `app/data/manse_corrections.json`의 `lunar-leap-flags-v1` 교정표에 원본 출처·날짜·기존 값·교정 값과 근거를 보관합니다. 0은 일반 달, 1은 윤달입니다.

| 양력 날짜 | 음력 날짜 | 원본 값 | 조회 시 적용 값 |
|---|---|---:|---:|
| 2017-06-23 | 2017년 5월 29일 | 1 | 0 |
| 2017-07-22 | 2017년 윤5월 29일 | 0 | 1 |
| 2020-05-22 | 2020년 4월 30일 | 1 | 0 |
| 2020-06-20 | 2020년 윤4월 29일 | 0 | 1 |
| 2023-03-21 | 2023년 2월 30일 | 1 | 0 |
| 2023-04-19 | 2023년 윤2월 29일 | 0 | 1 |
| 2025-07-24 | 2025년 6월 30일 | 1 | 0 |
| 2025-08-22 | 2025년 윤6월 29일 | 0 | 1 |
| 2028-06-22 | 2028년 5월 30일 | 1 | 0 |
| 2028-07-21 | 2028년 윤5월 29일 | 0 | 1 |

음력 조회는 먼저 해당 년·월·일의 **모든 후보**를 읽고, 원본 출처와 예상 행이 일치하는지 확인한 뒤 교정된 윤달 여부로 선택합니다. 따라서 2023년 일반 2월 29일은 3월 20일, 윤2월 29일은 4월 19일로 각각 변환됩니다. 양력 조회의 음력·윤달 응답에도 같은 교정을 적용합니다. 원본 SQL, `tb_manse`, `metadata()` 및 `iter_records()`의 값은 바꾸지 않아 재적재 해시 검사와 `already_present` 동작을 유지합니다.

교정표의 원본 출처·예상 값이 DB와 다르면 임의 적용하지 않고 `503 manse_unavailable`로 중단합니다. 검증된 교정 뒤에도 중복이 남으면 `422 ambiguous_lunar_date`로 안내합니다. 실제로 존재하지 않는 윤달 30일은 `422 invalid_lunar_date`입니다. 년·월·일 간지, 절입 시각 및 ASP 판정 공식은 이 교정의 대상이 아닙니다.

근거는 한국천문연구원의 [2017년 월력요항](https://astro.kasi.re.kr/life/pageView/1), [2020년 역서](https://astro.kasi.re.kr/file/astro_almanac_pdf/20200624134708539.pdf), [2023년 역서](https://astro.kasi.re.kr/file/astro_almanac_pdf/20221209095149975.pdf), [2025년 달력자료](https://astro.kasi.re.kr/life/post/calendardata), [2028년 달력자료](https://astro.kasi.re.kr/kor/life/post/calendarData?search_year=2028)입니다. 월력 자료에 제시된 초하루·월 길이·다음 달 초하루로 말일을 대조했습니다. 2028년 자료는 기관 제공 예측자료이며 공식 월력요항 발표 전 자료입니다. 독립 음력 라이브러리는 개발 검증에서만 참고하며 실행 중 값을 재계산하지 않습니다.

## ASP 규칙과 남은 범위

`y_gan/y_ji`, `m_gan/m_ji`, `d_gan/d_ji`는 기존 년·월·일주로 대응합니다. 홀수 절기 당일 해당 분부터 월주를 올리고, 입춘이면 년주도 올립니다. 시주 계산 후 00:30 이전 일주 보정 및 프로필별 23:30 야자시 규칙을 보존합니다. 월간 un은 ASP처럼 절입 당일 시각 비교 없이 월주를 올립니다.

이 SQL에는 `disp_day`, 연간 un의 `yearfortune` 판정 데이터, 궁합 분류표 및 직업 DLL이 없습니다. 이 의존성들은 여전히 미확보이며 기존 진단 안내를 유지합니다. 월간 표시기간은 DB 절입에서 파생합니다. DB 시작 전 절기가 필요한 1900-01-01~01-05 월간 요청은 명확한 오류로 안내합니다. ASP 상용 서버의 실제 실행 결과와 전 날짜 대조는 별도 검증 사항입니다.
